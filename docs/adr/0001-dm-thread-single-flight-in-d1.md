# 0001 — DM Thread รับข้อความทีละข้อความด้วย lease lock ใน D1

- สถานะ: Accepted
- วันที่: 2026-10-30

## บริบท
`POST /api/chats/:creator/message` อ่าน `relationships` ก่อนเรียก Gemini (อาจใช้เวลาหลายวินาทีถึง 20 วินาทีขึ้นไป) แล้วเขียนค่าทั้งแถวกลับด้วย upsert ถ้าผู้เล่นคนเดียวกันส่งข้อความซ้อนใน DM Thread เดียวกัน (กดรัว, สองแท็บ) ค่าที่เพิ่มของคำขอแรกจะถูกเขียนทับ (lost update) และ `rule_uses` อาจเกิน `maxUses` ได้ การตรวจและหัก Energy ก็แยกเป็นสองคำสั่ง ทำให้ยอดติดลบได้

ขนาดระบบ: ผู้เล่นล็อกอินเท่านั้น, ออนไลน์พร้อมกันประมาณ 100 คน, บนเว็บอย่างเดียว ผู้เล่นต่างคนกันไม่แย่งข้อมูลกัน ปัญหาเกิดเฉพาะภายใน DM Thread เดียวกัน

## การตัดสินใจ
1. DM Thread หนึ่งรับข้อความได้ครั้งละหนึ่งข้อความ ใช้แถว lease lock ใน `dm_threads` คีย์ `(user_id, creator_id)` หมดอายุ 90 วินาที (ครอบคลุมการเรียก model หลักสูงสุด 3 ครั้ง ครั้งละไม่เกิน 20 วินาที บวกรอบ knowledge อีก 20 วินาที) ถ้าถูกถือครองอยู่ให้ตอบ `409 thread_busy` และหน้าเว็บแสดงสถานะ "กำลังพิมพ์…"
2. การเปลี่ยนค่าความสัมพันธ์ใช้การบวกส่วนต่างแบบ atomic ในคำสั่ง SQL (เช่น `closeness = MIN(100, MAX(0, closeness + ?))`) แทนการเขียนค่าที่คำนวณไว้ก่อนเรียก AI
3. การหัก Energy เป็นคำสั่งเดียวที่มีเงื่อนไข `free + purchased >= 1` พร้อม `RETURNING` ถังที่ถูกหัก และคืนเข้าถังเดิมเมื่อ AI ล้มเหลว ทุกการเปลี่ยนแปลงบันทึกใน `token_ledger`

## ทางเลือกที่ไม่เลือก
- **Durable Object ต่อ DM Thread**: เรียงคิวข้อความได้สมบูรณ์และไม่ต้องปฏิเสธข้อความ แต่เพิ่มชิ้นส่วนโครงสร้างระบบใหม่และการ deploy ที่ซับซ้อนกว่า ซึ่งยังไม่คุ้มที่ 100 ผู้เล่น
- **Optimistic version column อย่างเดียว**: ตรวจพบการชนได้แต่ต้องเรียก Gemini ซ้ำหรือทิ้งคำตอบ ซึ่งเปลืองค่าใช้จ่ายและสับสนสำหรับผู้เล่น
- **Postgres + Redis lock**: เพิ่ม infrastructure นอก Cloudflare โดยไม่จำเป็น

## ผลที่ตามมา
- ผู้เล่นที่ส่งข้อความซ้อนจะเห็นสถานะรอแทนการได้คำตอบสองชุด
- ถ้า Worker ล้มกลางทาง lock จะหมดอายุเองใน 90 วินาที
- ถ้าภายหลังต้องการต่อคิวข้อความแทนการปฏิเสธ หรือมีผู้เล่นเพิ่มขึ้นมาก ให้พิจารณาย้ายไป Durable Object ได้โดยไม่ต้องเปลี่ยน schema ความสัมพันธ์

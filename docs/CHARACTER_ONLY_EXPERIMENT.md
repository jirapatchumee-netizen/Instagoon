# Character-only DeepSeek experiment

## Cheer response contract experiment (2026-11-08)

Cheer defaults to the `contract` variant using v2 in `content/creators/cheer/response-contract.md` (2,372 trimmed characters after the concise-banter revision). The original v1 is retained verbatim in `response-contract-v1.md` (2,093 characters). The build embeds both, but sends only the selected guide to DeepSeek. No filesystem read or second model call occurs during a turn. The original biography, authored opening, model alias and generation settings are unchanged. The Markdown contains principles, not scripted replies; it does not implement a fictional clock.

The revised v2 prioritizes distinct, compact spoken beats. For a short ordinary player reply it instructs one or two dialogue beats and zero to two meaningful action beats, at most four total; complex events may expand. It explicitly separates this from the longer authored opener, removes the expectation of an activity in every turn, and discourages repeated concessions or bargaining for a smaller version of a rejected item. A witty verbal continuation is enough. These are model instructions, not a silent truncator or guarantee of stylistic compliance. Explicit stops/topic changes remain respected. The changed text hash automatically selects fresh v2 history without deleting older runs; use per-turn hashes when comparing revisions carrying the same v2 label.

The chat settings menu selects **Contract v2**, **Contract v1** or **ชุดเดิม**. GET uses `responseVariant=contract|contract-v1|baseline`; message/reset POSTs carry the same field. Switching loads that variant's history before allowing messages. Reset clears only the selected variant and optional mode. No other character can configure this contract.

The baseline adds no fields to the previous experiment-key calculation, so baseline history stays reachable. Selecting `contract-v1` reproduces the original v1 identity; it does not gain v2 rules. Contract identity hashes the version and compiled text; v2 also fingerprints its action policy. Normal/optional-mode histories remain separate in all variants. Opening/switching makes no provider call and consumes no energy.

V2 validates player-action excerpts conservatively: marked actions are retained, recognizable first-person physical actions and physical-action requests are accepted, and ordinary speech/questions/future/hypothetical excerpts are omitted from the player's action frame. Requests use a distinct label rather than asserting completion. This bounded syntax check is not a general Thai semantic classifier; unusual unmarked descriptions may be omitted. Marked action syntax remains available. Provider wording and original JSON remain stored; v2 projects corrected `playerActions` into subsequent model context so misclassified speech is not reinforced. Baseline/v1 formatting and raw model history stay unchanged.

Migration 0016 adds `experiment_chat_traces`, also bootstrapped with existing experiment tables. Each successful generated reply atomically stores non-secret provenance: selected variant/mode, source/contract hashes, configured/resolved model, unchanged generation settings, action policy, usage and provider-call latency. Failed writes roll back/refund; reset/account deletion cascade. Existing messages have no trace and must not be labeled retroactively from current settings. Provider-call latency is distinct from existing full-turn latency metrics.

The authenticated player API exposes selected metadata and per-reply traces, never the optional secret prompt. The scoped Agent API reads traces when their table exists, returns the latest requested message window, and groups by player plus experiment key using opaque thread IDs. It never creates tables or syncs content from an agent GET. Contract reporting reads the real compiled `text`, computes its hash, and distinguishes the database definition from the deployed bundle so stale configuration is visible. Scope/auth remain unchanged. Existing turn metrics include opaque thread IDs for correlation. Compare within the same mode and matching inputs. The user chose live quality/latency evaluation on staging; local fixtures are not real DeepSeek measurements.

Suggested live comparison: start/reset each variant independently; send the same sequence, including rejecting the food offer, asking about a specific new topic, a clearly marked action, a hypothetical action, and an explicit request to stop/change topics. Compare specificity, thought/action/dialogue coherence, continuity, repetition and natural openings for a reply. Do not treat every refusal as a challenge or require a question at every ending. Repeat across fresh runs to observe variation.

## Optional scene presentation

The owner subsequently requested `chatExperiment.presentation=scene-v1`: Bangkok response time, model-chosen current location, a fictional inner thought and amber action frames alternating with spoken dialogue. The original biography remains the first system message unchanged; a separate short contract defines only these fields and their meaning. It gives no sample dialogue, banter strategy, pronouns, goal hierarchy or courtship/refusal policy. DeepSeek generates every character action, thought and spoken line in the same single call.

Player actions/requests must quote the latest input. Clearly marked `*actions*`, `[action: ...]` and `/me ...` are also placed in the action frame if the model omits them; quotations/hypothetical marker examples are not automatically enacted. Unmarked actions are identified by DeepSeek and require an exact source excerpt. The frame labels those excerpts `คุณ:` and does not invent acceptance or completion of a request. Ordinary dialogue does not require an action beat.

Migration 0015 and runtime bootstrap add a separate display table. Original provider JSON remains in model history; server-rendered time/labels never replace it. Display, raw message pair and thought are committed atomically and survive reload. Missing required fields or invented player-action evidence fail visibly, refund and do not trigger another provider. The presentation contract is part of the experiment identity, so enabling or changing it opens a separate empty run without deleting the earlier plain-text run.

Regression tests verify exact source-only payloads, old-state exclusion, fresh/new-run isolation, strict provider selection, visible errors without fallback, refunds, pair atomicity, locks and the legacy cleanup boundary. Mocked provider tests establish the integration contract; actual roleplay quality must be judged from live DeepSeek conversations.

## Optional mode and restored opening

The owner requested the Fifty Shades toggle on Cheer as well. `chatExperiment.allowFiftyShades=true` enables the existing protected mode provider without editing its text or mechanism. With the toggle off, no mode prompt is included. With it on, the existing server-resident prompt is inserted between the unchanged character source and the presentation contract. Adult consent still gates all chat access. DeepSeek remains the only generation provider, and tests exercise this wiring with generic fixture text rather than adult dialogue.

GET selects a mode with `fiftyShades=1`; message/reset POSTs select it with the boolean `fiftyShades`. Normal and enabled modes have distinct history keys, including a hash of the active mode prompt. The UI loads the selected history before applying the switch and blocks changing mode while a reply is pending. Switching back restores that mode's own conversation. Mode prompt text is never returned in API metadata.

Cheer's authored opening is restored from the earlier published character opening only (not the old biography, style examples or behavior rules). Its location, fictional thought and six ordered action/dialogue beats live under `chatExperiment.opening`. It is a free real assistant message, included in model history. Conditional writes and a deterministic scoped ID prevent duplicate greetings across tabs. Greeting and presentation commit atomically, with server time; a direct first POST also inherits the greeting. Resetting the selected mode allows its greeting to appear again. Adding/changing the opening selects a fresh run while retaining earlier experiment runs for comparison. No database schema change is needed because mode identity and greetings use the existing experiment key, role and display tables.

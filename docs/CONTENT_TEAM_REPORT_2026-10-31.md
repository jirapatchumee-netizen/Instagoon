# รายงานสำรวจระบบ Content และข้อเสนอประสานงาน Instagoon

วันที่: 31 ตุลาคม 2026  
สถานะ: **ผลสำรวจเบื้องต้นเพื่อให้ทั้งสองทีมพิจารณา ยังไม่ใช่การอนุมัติสถาปัตยกรรมหรือการเผยแพร่**

อ้างอิงแพ็กเกจ `CONTENT_AGENT_PACKAGE_2026-10-31.md` โดยให้ภาคผนวก ก และ ADR 0007 เป็นหลักสำหรับข้อตัดสินเฟส 1 รายงานนี้ไม่รวม credentials ข้อมูลผู้เล่นจริง หรือเนื้อหาที่ยังไม่เปิดเผย

## 1. ระบบที่สำรวจ

- NPC Studio บนเครื่อง: `F:/Instargoon` เป็นแอป React/TypeScript และ Node ใช้ SQLite และโฟลเดอร์ภาพบนเครื่อง
- สำเนา repository สำหรับงานร่วม: `F:/Instargoon/.local/instagoon-team-repo` สาขา `main` ที่ commit `bb607ca` ณ เวลาสำรวจ; ไม่ได้ยืนยันว่าเป็น commit ล่าสุดของ remote ในวันที่จัดทำรายงาน
- โปรแกรม Local เดิมเปิดด้วย `Start Studio.cmd`; สำเนาเว็บใช้ `pnpm --dir apps/froststory dev` และหน้า Studio ที่ `/studio.html` ตามสัญญาใน checkout ที่สำรวจ
- หลักฐาน Local: `lib/npc/store.ts`, `lib/npc/schema.ts`, `lib/npc/bundle.ts`, `components/`, `lib/npc/service.ts`
- หลักฐานฝั่งเว็บใน checkout: `src/modules/npc-studio/`, `apps/froststory/worker/src/index.mjs`, `apps/froststory/vite.config.ts` และ `docs/MULTI_AGENT_SYNC_CONTRACT.md`
- แพ็กเกจอ้างถึง path `apps/Instagoon/` ในหลายจุด ขณะที่ checkout ที่สำรวจมี `apps/froststory/` ต้องตรวจ path กับ commit ปัจจุบันก่อนลงมือ

## 2. Studio และ gameplay

Studio บนเครื่องรองรับการสร้างตัวละคร กฎความสัมพันธ์ ภาพรางวัล ความทรงจำ ทดสอบแชท ส่งออก/นำเข้า ZIP และติดตามการใช้ token ส่วนระบบเว็บใช้ Cloudflare Worker และ D1 โดยมีขอบเขตและพฤติกรรม gameplay ต่างจาก Local จึงยังยืนยันความเทียบเท่าไม่ได้จากชื่อ field เพียงอย่างเดียว

เป้าหมายในภาคผนวก ก คือ Studio สำหรับ content pipeline บน staging แยก build ออกจาก player และให้ logic รวมถึงข้อมูลที่ยังไม่ปลดล็อกอยู่ฝั่งเซิร์ฟเวอร์ ทั้งนี้รายการดังกล่าวเป็นเป้าหมาย ไม่ใช่หลักฐานว่าใช้งานครบแล้ว

## 3. ข้อมูลต้นฉบับและการกำหนดรุ่น

- Local เก็บ NPC เป็น JSON ในตาราง `npcs` ของ `data/studio.sqlite`; ภาพเก็บใน `data/assets/` ชื่อไฟล์อัปโหลดสร้างด้วย UUID
- `newNpc()` สร้าง ID แบบ UUID เป็นค่าเริ่มต้น; ค่าเริ่มต้นไม่ได้พิสูจน์ว่า ID ของตัวละครในเกมจริงเป็น UUID ทั้งหมด
- ZIP ประกอบด้วย `character.json`, `assets/`, `schema.json` และ README; ขั้นตอนนำเข้าของ Local สร้าง NPC ID ใหม่และชื่อไฟล์ภาพใหม่ จึงไม่เหมาะใช้เป็น upsert ตัวละครเดิมโดยไม่ปรับกระบวนการ
- รุ่น schema ของ NPC คือ `1.0`; ต้องตรวจ schema ฝั่ง Local กับ schema ใน repository ที่จะใช้งานจริง รวมทั้ง path ของภาพ ก่อนอ้างว่าใช้แทนกันได้
- เป้าหมาย Git เป็นต้นฉบับและ D1 เป็นสำเนา ยังไม่ใช่วิธีเก็บต้นฉบับที่ Local Studio ใช้อยู่ ต้องสร้างเส้นทางส่งออกและตรวจความถูกต้องก่อนเปลี่ยนผ่าน

## 4. คำตอบเบื้องต้น OQ-1 — โครง `content/`

**ข้อเสนอ:** ใช้ `content/creators/<npcId>/character.json` และแยก `posts/`, `stories/`, `images/` ตามโครง default ในภาคผนวก ก เป็นจุดเริ่มต้น โดยกำหนด `<npcId>` ให้คงที่และผ่านกติกา ID ของ schema

**เงื่อนไขก่อนสรุป:**

1. จัดทำ mapping ระหว่าง ID ใน Studio กับ ID ของเกมที่มีอยู่ โดยห้ามสร้าง ID ใหม่ทุกครั้งที่นำเข้าเพื่ออัปเดตตัวละครเดิม
2. กำหนด mapping จาก path Local เช่น `assets/<uuid>.<ext>` ไปยัง media key ที่เกมรองรับ และตรวจการชนกันของชื่อ
3. พิสูจน์การส่งออก ตรวจด้วย `NpcSchema` v1.0 และนำกลับเข้าทดสอบด้วยข้อมูลจำลอง โดยรักษา ID และอ้างอิงภาพตามข้อตกลงใหม่
4. ตกลง schema และแหล่งต้นฉบับของ post/story แยกต่างหาก เพราะยังไม่ได้พิสูจน์ความเข้ากันได้กับโครง default
5. ตรวจสิทธิ์เข้าถึง Git และแนวทางป้องกันเนื้อหาลับก่อนนำ definition หรือภาพที่ยังไม่ปลดล็อกเข้า repository

**ยังไม่ทราบ:** รายชื่อ mapping ตัวละครที่พร้อมปล่อยและความเข้ากันได้ของโพสต์/สตอรี่ทั้งหมด ต้องสำรวจไฟล์ต้นฉบับและ schema ของเวอร์ชันที่ทีมจะใช้ร่วมกันก่อนยืนยัน

## 5. คำตอบเบื้องต้น OQ-2 — ภาพและสื่อ

**ข้อเสนอ:** เริ่มประเมินค่า default ของภาคผนวก ก คือ D1 `media_blobs` จำกัด 900 KB ต่อไฟล์ และ CI ปฏิเสธไฟล์เกิน โดยตัดสินหลังได้ตัวเลขจริง แผน R2 อยู่เฟส 2 เว้นแต่หลักฐานด้านขนาดหรือปริมาณแสดงความจำเป็น

**ยังไม่ทราบ:** จำนวน ขนาด และชนิดไฟล์แยกตาม NPC ที่ใกล้ปล่อย; รายการ media key ที่ตรงกับไฟล์จริง; แผนวิดีโอ; ความเหมาะสมของภาพ; และผลทดสอบสิทธิ์เข้าถึงภาพที่ล็อก ไม่ควรนำจำนวนไฟล์ทั้งหมดในโฟลเดอร์มาแทนตัวเลขชุดพร้อมปล่อย

สำรวจแบบอ่านอย่างเดียวเพื่อจัดตาราง: NPC, ประเภทสื่อ, media key, ขนาด byte, ชนิดไฟล์, เกิน 900 KB หรือไม่ และสถานะตรวจสิทธิ์ โดยไม่แนบภาพหรือเนื้อหารางวัลที่ยังไม่เปิดเผยในรายงาน

เอกสารต้นทางรายงานภาพของเนยและพิมหก key ว่าหาย แต่ยังไม่ได้ตรวจ production ในการสำรวจนี้ จึงยังยืนยันสถานะปัจจุบันไม่ได้

## 6. การทดลองเล่นและจุดเชื่อมต่อ

Local ต้องใช้ Node และฐานข้อมูล/ภาพในเครื่อง; แชท AI ต้องใช้บริการและการตั้งค่าผู้ให้บริการที่เกี่ยวข้อง เว็บใช้ Worker/D1 และระบบยืนยันตัวตนของ environment นั้น ความสัมพันธ์ ความทรงจำ รางวัล และพฤติกรรม retry ระหว่างสองระบบต้องมีชุดทดสอบเปรียบเทียบก่อนถือว่าเหมือนกัน

API และ host matrix ใน `docs/api-contract.md` ของแพ็กเกจเป็น contract เป้าหมาย: prod ไม่เปิด Studio/admin/dev; staging เปิดเฉพาะส่วนที่จำเป็นหลังตรวจ allowlist; การเขียนข้อมูลเนื้อหาเกิดผ่าน CI ทั้งนี้ต้องตรวจ implementation และ environment จริงแยกจากเอกสารก่อนสรุปว่าได้บังคับใช้แล้ว

## 7. แผน staging เผยแพร่ และกู้คืน

1. ตอบ OQ-1 และ OQ-2 พร้อมหลักฐานให้ทั้งสองทีมภายใน **4 พฤศจิกายน 2026** ก่อนเริ่มเขียน sync script
2. พัฒนาเครื่องมือส่งออกและ validator บนเครื่องโดยใช้ข้อมูลจำลอง; ตรวจ schema, ID, media key, ขนาด และไฟล์อ้างอิงครบ
3. จัดทำ PR และ dry-run validation; หลังทีมอนุมัติแนวทางจึงสร้าง sync แบบ idempotent พร้อม append-only audit ตาม contract
4. ทดสอบชุดที่ระบุ commit SHA บน staging ด้วยข้อมูลทดสอบแยกจากผู้เล่นจริง รวมการระงับเนื้อหา การอ้างอิง revision เดิม และการจำกัดงบ AI
5. พิสูจน์ migration `0007` แบบ additive และการเผยแพร่/ย้อน revision เดิมด้วยข้อมูลทดสอบ โดยตรวจว่าไม่เขียนทับข้อมูลผู้เล่น; การดำเนินการจริงเป็นหน้าที่ผู้มีสิทธิ์และต้องทำตาม runbook และการอนุมัติของทั้งสองทีม

การ rollback เนื้อหาด้วย SHA เดิมเป็นเป้าหมายที่ต้องทดสอบจริง ยังไม่ควรถือว่ากู้คืนได้จนกว่าจะพิสูจน์กับ schema, media และผู้เล่นที่ผูก revision เดิม

## 8. ข้อขัดแย้งและประเด็นรอตัดสินใจ

- คู่มือภาพหายในแพ็กเกจยังแนะนำอัปโหลดเข้า production ผ่าน Studio และ passcode ซึ่งขัดกับภาคผนวก ก ให้ยึดภาคผนวก ก และแจ้งทีมแก้เอกสารต้นทาง
- ข้อเสนอ static assets เป็นทางเลือกในเอกสารสื่อ แต่ OQ-2 ยังกำหนด D1 เป็น default ชั่วคราว; ยังไม่เริ่มย้ายสื่อก่อนตกลง
- ADR 0007 supersede เฉพาะข้อ air-gapped ของ ADR 0006; หลักการปกป้อง runtime ฝั่งเซิร์ฟเวอร์ยังคงอยู่
- ต้องยืนยันการแยก build, Gmail session, allowlist, การปิดเส้นทางบน production, revision retention, audit และขีดจำกัด AI จากโค้ดและ environment จริงก่อนอ้างว่าเสร็จ
- นโยบายการเก็บเนื้อหาที่ยังไม่เปิดเผยใน Git และการป้องกัน reward media ต้องตกลงร่วมกันก่อนส่งไฟล์จริง

**ขอบเขตรอบนี้:** สำรวจและเสนอแผนเท่านั้น ไม่มีการ deploy, migration, push, เขียนข้อมูล production หรือขอ credentials
